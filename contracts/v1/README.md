# Frontline HTTP contract v1

`docs/p0-execution-record.md` freezes endpoint ownership and the canonical source revisions. This file records the v1 JSON shape; the API validates writes in `server/api/contracts.js`, and shared generated types remain a Cloud task. A preparation start returns `202 {preparationId,state,expiresAt}`; scope remains in a secure HttpOnly same-site cookie. A preparation read returns the canonical state, revision, sourced profile, gaps and capability manifest. A demo start accepts `{preparationId,expectedRevision,mode}` where mode is `business_demo` or `frontline_qa`. The server derives all authority and pinned version IDs; the browser supplies no business facts, tool IDs or agent policy.

The API must return `voice_unavailable` honestly if LiveKit credentials, worker dispatch or the configured paid-spend ceiling are unavailable. Simulated appointment requests stay private to a demo and never become answerable business facts. No success response may claim a real booking or a sent business request.

## Current local API handoff

The local Node API is mounted at `/v1`. `GET /v1/session` sets a readable `fl_csrf` cookie and returns `{csrfToken}`. The browser uses `credentials: 'include'` and sends `X-Frontline-CSRF: <csrfToken>` on subsequent scoped calls. The token can be reused for this page session. Browsers supply `Origin` on writes; client JavaScript must not set that header itself. The first preparation write sets the `fl_workspace` HttpOnly, SameSite=Strict capability cookie. All anonymous records expire after 24 hours.

`POST /v1/preparations` accepts `{url}` and returns `202 {preparationId,state:'researching',expiresAt,requestId,version}`. `GET /v1/preparations/:id` returns `{preparationId,state,readiness,revision,profile,gaps,capabilityManifest,availableModes,knowledgeRevisionId,agentVersionId,error,expiresAt,requestId,version}`. A completed profile has `{businessName,location,services:[{name,sourceUrl,evidence}],hours:{label,basis,sourceUrl,evidence}|null,sources:[]}`. Eligible preparations offer `['business_demo']`; insufficient context offers `['frontline_qa']`.

Production preparation admission requires `migrations/005_preparation_jobs.sql` and a running preparation worker. The workspace state, preparation record, and admitted job commit in one Postgres transaction, including for a new anonymous scope; a denied admission rolls back all three. Admission is serialized in Postgres, using a hash of the validated client address plus workspace and global limits. It returns `429 rate_limited` or `429 inspection_busy` when full and `503 inspection_unavailable` when the queue cannot admit work. Accepted jobs have leases, two bounded retries, and restart recovery. An exhausted job becomes `failed_retryable` on the scoped preparation. Development uses a single-process bounded queue; it is not a production rate gate. For reverse-proxy deployment, set `FRONTLINE_TRUSTED_PROXY_IPS` to the exact peer address or comma-separated addresses and configure ingress to overwrite `X-Frontline-Client-IP` with one validated client IP. The API ignores that header from all other peers and closes preparation if a configured proxy omits or malforms it. Keep the API port inaccessible except through the configured ingress.

An eligible manifest has `{knowledgeCoverage:'sourced'|'partial',actionReadiness:'intake_only',capabilities:[{topic,context,canDoNow,cannotDecide,handoff}],limits?:string[]}`. Each capability describes what Bob can answer or collect, what remains undecided, and the honest human route. The API refuses to publish business readiness without sourced identity and service facts. It compiles the manifest from the bounded website preparation result.

`POST /v1/demos` accepts `{preparationId,expectedRevision,mode:'business_demo'|'frontline_qa'}`. With a configured voice adapter and enforcing paid-start reservation, its `201` response is `{demoId,mode,livekitUrl,participantToken,tokenExpiresAt,setupDeadlineAt,expiresAt,requestId,version}`. `tokenExpiresAt` is the short-lived browser grant expiry; `expiresAt` is the 24-hour workspace expiry. The initial connection must become media-ready before the server-owned 20-second `setupDeadlineAt`. Until dispatch, credentials, budget limits, and the durable watchdog are ready, it returns `503 voice_unavailable`. `GET /v1/demos/:id` and `/result` return a scoped `{demoId,state,mode,setupDeadlineAt,startedAt,softCloseAt,hardEndAt,appointmentRequest,expiresAt}`. `POST /v1/demos/:id/end` deletes the room before marking the demo ended.

Internal worker calls use `Authorization: Bearer <FRONTLINE_VOICE_SERVICE_TOKEN>` and `X-Frontline-Room`, `X-Frontline-Generation`, `X-Frontline-Agent-Version-Id` bound to the demo. Implemented paths are `GET /v1/internal/demos/:id/runtime` and `POST /v1/internal/demos/:id/{ready,lookup-business-fact,lookup-frontline-fact,update-simulated-request}`. Ready stamps server deadlines only when a voice adapter verifies both media participants. The legacy request-update route currently accepts a model-supplied `callerConfirmed` boolean; it is **not compliant with the frozen workflow-write contract and must not authorize a save**. Downstream API integration replaces that authority with the server-recorded caller-turn/readback/revision binding in `confirmation.schema.json` and `http-endpoints.json`. The server adds `simulation:true`, `deliveryState:'not_sent'`, `bookingState:'not_booked'`, and pins the demo/knowledge/agent revisions. It never indexes these private fields as business facts.

Fallback dispatch uses the platform runtime version `frontline-qa-v1` in worker metadata and the private runtime bundle. The fallback demo still has no business agent version; its `mode` remains `frontline_qa`, and it cannot call business lookup or appointment intake.

With no `DATABASE_URL`, this checkout uses an atomic single-process development file store under `work/`. With `DATABASE_URL`, it uses `server/api/postgres-store.js` and requires migrations 001 through 006 applied by a migration owner plus a separate runtime role named `frontline_app`. That adapter stores one private JSONB aggregate per owner scope, with transaction-local scope and forced row-level security. It is an interim persistence shape, not the normalized production model in `docs/architecture.md`; it has not been exercised against a live Postgres instance here. The bounded research output now compiles cited business facts and the manifest above. The Frontline Q&A fallback uses three approved product facts and never reads business or customer records. Production database verification, LiveKit dispatch, and independent room deadline enforcement remain required before enabling public voice.

`migrations/002_voice_budget.sql` adds an atomic paid-start reservation function and an identity-free UTC daily budget ledger. The API gate requires `FRONTLINE_VOICE_SPEND_CAP_USD`, `FRONTLINE_VOICE_MAX_SESSION_USD`, and `FRONTLINE_VOICE_GLOBAL_CONCURRENT_MAX` to be positive. The max-session value must be a provider-validated conservative upper bound for the 20-second setup plus five-minute room, including speech/model charges, not an average estimate. It reserves that full amount against the UTC daily cap, enforces one active demo per workspace, three starts per workspace per day, and global concurrency. A reservation has a ten-minute TTL for an orphaned start, but remains active for concurrency while its deadline ledger row is active, even if LiveKit room deletion fails. The daily ledger retains the reserved amount after anonymous-scope cleanup; it decreases only when dispatch failed and room deletion was confirmed. Actual provider usage reconciliation and pricing validation are still required before public exposure. The local file store uses the same limits for one process but cannot enable public paid voice. `migrations/003_demo_deadlines.sql` adds a restart-safe setup/conversation deadline ledger. In production only, `FRONTLINE_ENABLE_PAID_VOICE=true` lets server startup enable paid starts after the migrations, a non-bypassing Postgres role, LiveKit credentials, a worker service token, a successful initial deadline sweep, and a healthy watchdog. The API checks watchdog health before every reservation. Missing or unhealthy prerequisites keep `POST /v1/demos` at `503 voice_unavailable`. No production database or LiveKit account has been exercised here.


## TOM-19 shared workflow freeze

Canonical machine-readable files are under `schemas/`, with the exact six workflow/tool mapping and 20/270/300-second deadlines in `workflows.json`. `http-endpoints.json` freezes internal request/response semantics for preparation/knowledge, API/data, voice, and results consumers. `typescript/index.ts` and `python/frontline_contracts.py` are dependency-free consumers. `contract-validator.js` is an executable structural/semantic guard for fixtures and boundary inputs.

Office hours, service hours, and appointment hours are separate fact groups and profile groups. No consumer may promote one to another. Appointment lookup is discriminated: `not_found` is a successful scoped lookup with no match; `unavailable` is lookup failure; `verification_required` reveals no appointment detail. Request/case/escalation operation receipts are append-only, payload-hash/idempotency-bound outcomes. Terminal sessions set `reconnectAllowed:false` and reject mutation.

Schema or helper success does **not** prove authoritative backend enforcement. The API/data lane must load current server records inside its transaction, compare workflow revision, caller turn/sequence, field revision, readback revision and payload hash, persist the confirmation, enforce operation idempotence, and fence ending/terminal writes. The current `server/api/service.js` still creates a 60-second setup deadline and exposes the legacy request-update route; that file is outside TOM-19 ownership and is an explicit integration patch for TOM-20. `server/livekit-adapter.js` already bounds the 300-second active session (with retry tolerance); no owned adapter change was necessary.


### Frozen lane boundary after integration review

`http-endpoints.json` now references concrete JSON schemas. Routes marked `planned` are contracts for the API lane, not implemented endpoints. History extends the existing `/v1/agents/:id` and `/v1/workspaces/:id` route families with `/history`; authenticate membership in the claimed resource before returning private outcomes. Worker routes preserve the existing bearer, room, generation and pinned-agent authentication. `/turn` records finalized caller text and obtains Jev classification on the server. Worker-provided classifications or confirmation booleans are rejected by the input shape. Workflow events are server-created audit records, not an unrestricted worker write route.

Typed intake fields are `callerName`, `contactPhone` or `contactEmail`, `serviceNeed`, and `propertyCity`. Optional fields are property type, company, preferred day/window, timezone, recurrence and notes. Draft validation may have missing fields. Saved request records require the complete shape and exact caller confirmation binding. A confirmation must bind the latest caller ID and sequence, exact readback/hash/revisions, a positive server-classified dialogue act, and a turn after the readback. The API owner must enforce this against authenticated, server-loaded records in a transaction, including correct handling of negation and corrections.

Canonical schema enums are in `schemas/common.schema.json`; workflow/tool associations and deadlines remain in `workflows.json`. Run `python3 contracts/v1/generate-consumers.py` to regenerate TypeScript and Python wire types after changing schemas. Python exposes camelCase JSON wire keys through TypedDicts, not the previous positional dataclasses. Validate untrusted data with `validateContract`/`validate_contract`; type declarations alone are not runtime checks. The JavaScript validator is a server/Node consumer. Browser consumers import TypeScript types only. Shared fixtures live in `fixtures.json` and run in both JS and Python.

The session mutation guard accepts only `{status:'active',phase:<known nonterminal phase>}`. API adapters must map the existing demo `state` to this canonical guard explicitly. Ending, terminal, missing and unknown state are rejected. Receipt schemas discriminate `saved` with `recordId` from `failed` with `failureCode`. The dedicated ending/escalation/terminal routes implement bounded shutdown independently of storage or speech success. Consumers must not call the ordinary request-mutation guard to authorize the single escalation attempt bound to its ending transition.


Demo status preserves `mode`, `setupDeadlineAt`, `startedAt`, `softCloseAt`, `hardEndAt`, `appointmentRequest`, and `expiresAt` while adding terminal state/reconnect fields. `/v1/demos/:id/result` preserves those fields and requires scoped `requests`, `cases`, `lookups`, and `receipts` arrays before claim. The nullable legacy `appointmentRequest` is an unconfirmed draft, not a new saved outcome. Endpoint response refs validate the payload **after stripping exactly `requestId` and `version`**; `responseEnvelope` separately defines these existing flat HTTP metadata fields. Do not drop the browser's server deadline fields when integrating terminal state.

State-changing action responses return their committed `workflowRevision`; `/turn` returns it as `workflow.revision`. Field/readback/confirmation/lookup actions advance it once, and exact idempotent replay preserves the original response. Ending and terminal responses include both `stateRevision` and `workflowRevision`. Worker callers use the returned workflow revision for the next compare-and-swap action, including the bounded escalation after ending. Field revision and readback revision remain separate payload-confirmation counters.
